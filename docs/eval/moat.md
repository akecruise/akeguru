## Manual review (checkMoatGrounding can't check these)

**1. Does `scale_economies`/`process_power` actually cite a real Revenue/Margin number (moat.md rule #3)?** — yes on both runs: MSFT's `scale_economies` cites Revenue ($331.8B) + Gross Margin (67.9%) + Operating Margin (45.1%) + Revenue Growth (17.7%), all matching real facts; 1773.HK's `process_power` cites Operating Margin (27.2%), Net Margin (19.1%), Revenue Growth (14.2%). Neither is the free-floating "scale economies, trust me" claim the rule is meant to block.

**2. Do the qualitative types (`switching_costs` here, on both runs) cite genuine indirect evidence, or a fact grabbed just to pad `supportingFactIds`?** — reasonable, if a little formulaic: both runs justify `switching_costs` with margin/ROE figures ("high margin/ROE ⇒ pricing power ⇒ customers are locked in"), which is the same indirect-evidence pattern moat.md's example for `brand` suggests — margin as a proxy for pricing power. It's a legitimate link, though it's also the exact same justification style the model used for `switching_costs` on MSFT and `process_power` on 1773.HK ("margin is high, therefore X moat") — worth watching whether this model defaults to margin-as-universal-evidence for every qualitative type rather than picking type-specific signals (e.g. citing Revenue Growth stability specifically for `switching_costs`, not margin).

**3. Is `type: 'none'` avoided or used dishonestly?** — didn't come up: both tickers got 2 non-`none` items, and both sets of evidence look genuinely defensible given the facts available, not overreach. No test of the `none` path from a live run yet — would need a ticker with visibly weak/declining margins to see whether the model correctly reaches for `none` instead of forcing a moat narrative.

**4. Overlap between the 2 items in the same run?** — none: no `supportingFactIds` are shared between the two items on either ticker, and the two moat types picked (scale/process-power vs. switching_costs) are conceptually distinct, unlike risk's 1773.HK run where both items touched the same Total Debt figure.

No grounding failures on either run — nothing needed fixing this time (contrast with risk.md, where the first 1773.HK run needed a prompt fix for a computed-number false positive).

Both cited ids share the real id's exact 17-character prefix and diverge only in the trailing segment — close enough to look right at a glance, wrong when checked. The Gross Margin one reappears identically in *two* separate items (`process_power` and `brand`'s citations), not a one-off typo. All the surrounding numeric claims (67.94% gross margin, the operating income figures) were themselves correct — this was consistently a citation error, not a hallucinated value. 1773.HK, same ticker class as the clean gemini row above, had zero such issues.

**Contrast with gemini/ollama's failure modes so far**: qwen3:8b (ollama) fabricates ids that don't even try to look real (`moat001`, `fct001`); groq relabeled a real id to a completely different metric. claude-cli's MSFT failure here is neither — it's a real id with 1-2 characters wrong, indistinguishable from a real one without checking the DB. This is exactly the class of error `checkMoatGrounding`/`checkGrounding` exist to catch regardless of how subtle the mistake is — worth remembering as evidence that even a strong model + `--json-schema` structural constraints don't eliminate the need for the grounding-check gate.
